AIC: Sim-to-Real Cable Insertion Challenge
Intrinsic AI for Industry Challenge — Personal Project, 2026
Challenge Repo

End-to-end sim-to-real cable insertion stack for Intrinsic's AI for Industry Challenge — UR5e + Robotiq Hand-E with 3 wrist cameras and an ATI F/T sensor inserting SFP plugs into NIC card ports. Built data collection, training, and evaluation pipelines across Gazebo Harmonic (the eval simulator) and Isaac Lab (parallel collection), targeting both qualification phases and the public trials.

Key Contributions:

  • Native ROS2 Kilted Build: Built the full AIC stack from source (no Docker) with C++20 / gcc-13, including Gazebo + ros-gz bridge wiring and CablePlugin patches (detach_gripper / attach_gripper, disable_port_attachment) enabling multi-cycle data collection without losing the gripper-cable joint.
  • BCCheatCode Insertion Policy: Closed-loop PI controller on plug-to-port XY error with SLERP orientation interpolation — the controller that reliably inserts the flexible 80-link cable under the eval impedance controller, against which open-loop VF and OSC both failed.
  • Data Collection Pipelines: Authored VFCollectPolicy (recording wrapper for cameras, TCP pose, plug pose, F/T, joints, action deltas) and a Python trial orchestrator with board-only respawn that avoids arm sag. Collected 2 160 expert trajectories in parallel Isaac Lab environments.
  • Diffusion Policy Training: Trained LeRobot-style diffusion with classifier- free guidance on a port embedding and an auxiliary progress head; achieved val_chunk_mse < 0.04 on the combined far-spawn dataset.
  • Sim-to-Sim Engineering: Diagnosed and worked around Isaac ↔ Gazebo parity issues — 2× gravity-comp torque mismatch, ~35° insertion-axis bug on the IsaacLab side, and unreliable collision physics around SC ports — documenting the portable feature surface for cross-sim policies.
  • Flexible Cable Physics: Regenerated the cable as an 80-link / 12 mm chain with retuned joint stiffness and damping, producing a markedly more compliant cable than the upstream 20-link model and making PI-control insertion viable.

Stack: ROS2 Kilted, Gazebo Harmonic, Isaac Lab / Isaac Sim, LeRobot, PyTorch, MoveIt, OpenCV, MuJoCo. UR5e + Robotiq Hand-E + ATI F/T.

Learned the hard way:

  • Don't fake spawn poses with motion controllers. Five attempts to reposition the arm near the socket via VF pre-rolls, OSC waypoints, two-phase OSC, and an IK + spawn-cone teleport all failed (overshoot, below-table crashes, "two motions" artifacts, in-table spawns). The right answer is the boring one: drive the arm to a good pose with teleop, read the joints off the property panel, and hardcode them into init_state.joint_pos.
  • Open-loop control loses to flexible-cable dynamics. A flexible 80-link cable under an impedance controller produces sag, swing, and lateral levering. Pure P-control oscillates around the swing-induced steady-state error; only the integral term reliably zeroes it. Vector-field control is safe only for monotonic descent — never feed it an above-port waypoint, it will overshoot upward.
  • Read-after-write returns stale physics state. robot.data.body_pos_w after write_root_pose_to_sim in Isaac, or a TF lookup right after a Gazebo respawn, both return pre-write data. Always step the sim once or gate on a fresh /clock tick before consuming pose data — many "sign error" and "crashed into the table" bugs traced to this.
  • Sim-to-sim is not free. Isaac Lab and Gazebo do not agree: gravity-comp torques differ by 2×, the IsaacLab insertion axis is ~35° off because card rotation isn't applied to a hardcoded offset, and SC-port collisions are unreliable in both Gazebo and MuJoCo. Effort/torque features are non-portable — train on position / velocity if you want the policy to transfer.
  • Filter at collection time, not at training time. Bad trajectories left on disk get re-read every epoch and silently leak in when filter logic drifts. Classify and drop per-trial outcomes the moment they happen.
  • Long unattended runs die at the same threshold. CablePlugin segfaults around 140–150 sequential spawn/delete cycles (upstream entity leak). Batch collection in chunks of <120 episodes with a full Gazebo restart between batches.
  • Controller state carries between episodes. Without an explicit command-buffer zero and a joint-velocity ~0 check, the first step of every new trial gets a "kick" from stale commanded pose — matches the upstream init-sag report and corrupts the first frames of the bag.
  • Full robot+cable respawn breaks the impedance controller. Sudden cable load at spawn-time sags the arm and a stiffness ramp introduces new pathologies. Board-only respawn (delete and re-add just the task board) sidesteps it entirely.
  • Don't trust the Gazebo touch sensor alone. The contact collision box is 0.25 mm thin and the plug routinely misses it. Add a proximity-based fallback (e.g. 3 mm Z threshold) before declaring insertion done.
  • F/T tare doesn't tare the gravity bias. The wrist Fz reads ~20 N at init from the gripper's own weight, and contact actually decreases Fz as the normal force partially cancels gravity. Threshold on the delta from steady-state, not the absolute value.

STMPL: Human Body Soft Tissue Deformation Deep Learning Simulation
M.Sc Research Thesis, Technion, 2024
Project Page  /  Paper

Developed the STMPL model, an enhanced version of the SMPL model for realistic simulation of human soft tissue deformations optimized for real-time applications. The model maps 3D body data to 2D UV maps for efficient processing using a UNET-based architecture, achieving real-time inference speeds of 2ms with FEM-level accuracy while generalizing on unseen shapes and thicknesses.

Bitcoin Blockchain Simulation
Blockchain Technology Demo
Demo

A toy example of a Bitcoin Blockchain Simulator designed to be an interactive and educational web application. It visually demonstrates the fundamental principles of a cryptocurrency network with multiple nodes.

Key Features:

  • 🌐 Multi-Node Network : Simulates a network of nodes, visually representing their positions and connections. Users can add new nodes to see how the network expands.
  • 💰 Wallet & Transaction Management : Allows users to create new wallets, view balances, and send transactions between them. The simulation shows pending transactions in a mempool before they are confirmed in a block.
  • ⛏️ Proof-of-Work Mining : A mining process is simulated where a random node attempts to solve a cryptographic puzzle to create a new block. The successful miner receives a block reward and transaction fees.
  • ⛓️ Blockchain & Block Details : Nodes maintain their own copy of the blockchain. Users can inspect any node's blockchain to see the details of each block, including its hash, transactions, and the miner's nonce.
  • ⚙️ Dynamic Controls : Users can manually create transactions and start the mining process, or enable an auto system to run the simulation automatically. Controls for adjusting mining difficulty and network height are also available.
